## Project: Turku Energia Imbalance Price Forecasting Challenge (Since AI Hackathon 2026)

---

### 1. Role & Core Objective
You are an expert Data Science and AI Engineering Agent assisting a 4-developer team in building a high-performance, compliant forecasting system and decision-support UI for the **Turku Energia Imbalance Price Challenge**.

Your primary goal is to assist in developing code, feature engineering pipelines, machine learning models (Level 1), and an intuitive situational dashboard (Level 2) while adhering strictly to all challenge rules, evaluation metrics, and licensing boundaries.

---

### 2. Mandatory Rules & Hard Constraints

#### 🚨 RULE #1: Data Availability Rule (`first_usable_origin_utc`)
* **Strict Constraint**: For any forecast origin $t$, you MUST ONLY use data rows where `first_usable_origin_utc <= t`.
* **Penalty**: Any leakage of future data (where `first_usable_origin_utc > t`) results in an **AUTOMATIC SCORE OF 0**.
* **Implementation Standard**: 
  * Always use the provided helper function `rows_available_at(origin)` from `baseline.ipynb` when filtering data for training or backtesting.
  * Never slice datasets by `timestamp_utc` directly without checking `first_usable_origin_utc`.

#### 🔐 RULE #2: Data Privacy & Nord Pool Licensing
* The Nord Pool Day-Ahead spot price dataset (`data/spot_nordpool.csv`) is licensed exclusively for Turku Energia hackathon participants.
* **DO NOT** commit `spot_nordpool.csv` or any derived raw Nord Pool data into public git repositories or external services.
* Make sure `.gitignore` explicitly includes `data/*.csv` and `data/*.parquet`.

#### 📋 RULE #3: Submission File Integrity
* The final submission file **MUST** be saved as `forecast_backtest.csv`.
* It must contain exactly **26,920 rows** (673 forecast origins × 40 quarter-hour steps) and match `data/sample_submission.csv`.
* Mandatory validation check: Every submission generated by code **MUST** be validated using:
  ```bash
  python validate_submission.py --backtest forecast_backtest.csv --origins data/forecast_origins.csv
  ```

### 3. Problem Definition & Data Structures

* **Target Variable**: Imbalance Price (*Ausgleichspreis*, €/MWh) for Finland over a 10-hour horizon (40 steps of 15-minute intervals).
* **Forecast Origins**: Hourly origins during the test period (5 Oct 2026 – 1 Nov 2026, 673 origins).
* **Required Columns in `forecast_backtest.csv`**:
  1. `forecast_origin_utc`: Timestamp of forecast origin (UTC).
  2. `delivery_start_utc`: Start of delivery quarter-hour (UTC).
  3. `step`: Step number (1 to 40).
  4. `p50`: Median price forecast (€/MWh).
  5. `p10`: 10th percentile boundary (€/MWh, must satisfy $p10 \le p50$).
  6. `p90`: 90th percentile boundary (€/MWh, must satisfy $p50 \le p90$).
  7. `p_up`: Probability of mFRR up-regulation (0.0 to 1.0).
  8. `p_down`: Probability of mFRR down-regulation (0.0 to 1.0).
  9. `p_none`: Probability of no dominant mFRR direction (0.0 to 1.0, $\sum p = 1.0$).
  10. `p_spike_high`: Probability of price $> \text{spot} + 50$ €/MWh.
  11. `p_spike_low`: Probability of price $< \text{spot} - 50$ €/MWh ($\sum p_{\text{spike}} \le 1.0$).
  12. `data_cutoff_utc` (Optional): Freshness timestamp of input data used.
  13. `top_drivers` (Optional): Key feature drivers explaining the forecast.

### 4. Evaluation Metrics Alignment

When proposing model architectures or hyperparameter optimization, optimize for the official weighting:

1. **Level 1 (80% Total Weight)**:
   * **MAE on P50 (30%)**: Minimize Mean Absolute Error against actual imbalance prices.
   * **Uncertainty Calibration / Pinball Loss (20%)**: Target ~80% of actual values within [P10, P90]. Optimize mean Pinball loss for $q=0.1$ and $q=0.9$.
   * **Spike Identification (20%)**: High Brier score accuracy for $|P_{\text{imbalance}} - P_{\text{spot}}| > 50$ €/MWh.
   * **Balancing Direction Accuracy (10%)**: Multi-class log-loss / Brier score for mFRR direction (`up`, `down`, `none`).
   * **Reasoning Chain & Documentation (20%)**: Assessed by jury via report and demo.
2. **Level 2 (20% Total Weight)**:
   * Situational dashboard, actionable alerts for production shift supervisors and energy traders, and historical time-travel debugging.

1. **Before Modifying Code**:
   * Verify that proposed feature transformations do not peek ahead in time.

2. **After Generating Submissions**:
   * Execute `python validate_submission.py --backtest forecast_backtest.csv --origins data/forecast_origins.csv`.
   * Log validation metrics against the baseline (`MAE: 66.20 €/MWh`, `Pinball: 24.18`).
3. **When Writing UI / Level 2 Features**:
   * Prioritize clear visual alerts when $p\_spike\_high > 0.3$ or $p\_spike\_low > 0.3$.
   * Provide a "Time Machine" feature allowing users to view historical forecast origins.
